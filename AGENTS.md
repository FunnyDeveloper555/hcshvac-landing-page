# Architecture rules
- Bulk product parsing preserves original descriptions, extracts explicit labeled measurements, stores diameter and unmatched details in specifications (including Other products), and maps height/width/depth/weight to the existing page-level columns so review and saved products retain them.

- About Us uses section-specific child routes backed by the existing company JSONB settings; each editor saves only its own fields merged with the latest settings to preserve other sections.

- Legacy inbound Twilio chat media is recovered by the staff-authenticated chat-media function into private chat-files storage, with conversation access checks and signed URLs; never expose provider credentials or require public photos.

- Blue Flame's uploaded website lives as original static documents in public/blueflame-site; on its exact hosts main.tsx writes the page in place at the clean URL (/, /about.html) before React loads, so its HTML/CSS/JS never mixes with the CRM or other companies.
- Service Directory settings are company-scoped JSONB; the editor reads defaults (headings + each panel's sub-content cards) from the uploaded template and the website applies only text/list changes inside existing markup, so accordion layout and scripts stay intact.

- Customer submission action alerts read actual pending customer/appointment records through the staff-only crm_pending_submissions RPC; staff saves clear review markers, while reading messages never dismisses unfinished work.
- Sidebar and customer/appointment list pending indicators derive record IDs from the same usePendingSubmissions query as the alert list, so they remain synchronized without independent read/dismissal state.
- Pending submission dot age is calculated by submissionAgeStage from the alert's submitted_at; menu dots use the oldest unfinished submission of the corresponding kind so escalation stays consistent across views.

- Apply Open appointment date priority before pagination through the appointment ordering helper; today's work must not be buried on later pages while historical views keep their existing order.- Admin chat lives in chat_conversations/chat_members/chat_messages; all sends go through the chat-send function so outside texts and away-staff alerts happen server-side, and inbound texts route to whichever chat or ticket/task texted that number most recently.
- Text-thread display names come from the staff-only chat_external_names() RPC, which matches a thread's phone against customers, vendors, employees and bookings and backfills chat_conversations.external_name, so the CRM shows who a number belongs to everywhere instead of a bare phone.
- Installation warranty/maintenance colors come only from src/components/admin/installations/warrantyStatus.ts; appointments whose visit type mentions installation cannot close (manually or by the auto-close job) without an installation record, so the closeout rule stays in one place per layer.
- Extra alert recipients (pagers, office lines) live in public.notification_targets; appointment-sms includes active rows in appointment texts (notify_appointments) and submission alerts (notify_submissions), so new recipients are data changes, not code changes.
- Appointment and manual SMS identify pager recipients from notification_targets email domains and use the shared pager formatter; single-segment printable ASCII avoids legacy pager Unicode/multipart display failures without altering email content.
- Appointment close-out goes through CloseAppointmentDialog (visit summary required, photos/videos optional, stored in the private appointment-files bucket under the appointment id); cancellation goes through CancelAppointmentDialog (reason required) — both live in src/components/admin/appointments/CloseAppointmentDialog.tsx so the close/cancel buttons never flip status directly.
- Booking invitations can carry an optional assigned_employee_id (chosen in SendInvitationDialog); submit_appointment_request copies it onto the new appointment so the job lands on that person's calendar.
- Appointment time dropdowns use timeSlotsWith() from src/lib/timeSlots.ts so customer-submitted times outside the standard 2-hour windows (e.g. "16:30") stay visible instead of rendering blank; SubmissionDetailsDialog has the Modify date/time flow with Save vs Update client (SMS + confirmation email).
- Unanswered inbound chat texts escalate via the scheduled chat-escalate function (10-min wait, one alert per conversation, marked by chat_messages.escalation_sent_at) to notification_targets rows with notify_chat, so recipients are data changes.
- Blue Flame products.html/product-detail.html replace the bundled products-data.js with live "showing" Products module rows (src/lib/blueFlameProducts.ts maps them to the template HVAC_PRODUCTS shape), so the catalog is managed only in the Products module.
- Add New Product keeps Product Type required and renders each type's sheet fields through visibleSpecFields() in src/lib/productSpecs.ts, which hides the height/width/depth/weight copies because the page's Model & Dimensions card owns those columns the website reads.
- Blue Flame services.html editing is config-driven by SERVICES_SECTIONS in src/lib/blueFlameServicesPage.ts (stored in companies.services_page per section key), so the editor, defaults and website stay aligned from one definition.
- Pricing rules live in public.pricing_rules; selling price math and rule matching (company+type > type > company > default) are only in src/lib/pricingRules.ts so every screen prices the same way.
- Bulk pricing writes products.selling_price/pricing_rule_id from the Products List selection via BulkPricingDialog; Our Cost is read only through productOurCost() in src/lib/pricingRules.ts so every screen agrees on cost.
